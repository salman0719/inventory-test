## Recorded risks after Gate A

- **Cafe depth (high).** No recipes or POS depletion, so the cafe demo covers
  purchasing, receiving, wastage and count correction only. The walkthrough must
  state that rather than imply usage tracking.
- **Mobile receiving (medium).** Receiving and wastage happen on a phone; a
  desktop-only form fails the staff persona and the demo.
- **Partial receiving correctness (high).** Double-counting stock is the classic
  defect; receiving must be one atomic transaction with tests.
- **Single-PO model (low).** Users of split-PO tools may expect suffixed orders;
  outstanding quantities must be labelled plainly.
- **No validation yet (high).** Personas are hypotheses until Phase 7.

## Risks to actively monitor

- Stock ledger and cached quantity becoming inconsistent.
- Partial receiving creating duplicate stock movements.
- Cross-business data exposure due to missing or weak RLS.
- Demo reset deleting the wrong business data.
- UI controls that look functional but are not connected to real operations.
- Seed data that does not support a believable demonstration.
- Excessive scope expansion into ERP functionality.
- Third-party service costs or account changes made without approval.

Local JWT verification is the open fix for the first row: replacing the proxy's
`auth.getUser()` with `getClaims()` removes that round trip, but only if the
Supabase project signs JWTs asymmetrically and publishes a JWKS — otherwise
`getClaims()` falls back to the same network call.

Confirmed 2026-11-22: it does. `/auth/v1/.well-known/jwks.json` answers 200 with a
single `EC` key, `alg: ES256`, kid `00efa8a1…`, and a decoded session access-token
header carries the same `alg` and kid, so the tokens on this project are
asymmetric.

Implemented 2026-11-22: the proxy calls `getClaims()` and measures 3.1 ms p50 /
11.2 ms p95 across 40 signed-in navigations, with no `getUser()` calls in the
window, down from 89.3 / 623.0 ms. `getUser()` remains the fallback for requests
local verification cannot decide, and is still what refreshes cookies. What is left
of this item is the page's own `getSessionUser()`, which is now the whole of a
navigation's auth cost.

Measured 2026-11-22 (`NAV_TIMING=1`, 40 signed-in navigations, dev server on
Windows against Docker Postgres): each of the two auth checks is 89–93 ms at p50
and 510–623 ms at p95, so together they are the larger half of a navigation's
server time; the three transactions a products page opens cost about 75 ms p50, of
which `tenant.setup` (begin, role, claims) is the largest single component at
112 ms p95. Numbers are per layer, not wall clock. After the same-day change to
one transaction per page and a one-statement begin, `tenant.setup` fell to 4.8 ms
p50 / 11.6 ms p95 and a page takes two transactions instead of three; the auth
rows stayed where they were within noise, so they remain the open item.

Correction (2026-11-22): the page-level duplicate is smaller than previously
recorded here. `getSessionUser()` and `getActiveBusiness()` are both wrapped in
React `cache()`, so the calls in `products/page.tsx` and in `AppShell`
(`BusinessSelectorSlot`, `UserMenu`) collapse into one per render. A navigation
costs two Supabase auth round trips — one in `proxy.ts`, one in the render — not
four. Only two things remain open: `getClaims` in the proxy, and whether the two
reads can be cut to one by passing the session down instead of verifying again.

Implemented 2026-11-23: the render path no longer calls Supabase. `src/proxy.ts`
forwards what it verified as request headers — `x-verified-user-id`, plus a
percent-encoded `x-verified-user-email` when the session carries one — and
`src/lib/session.ts` reads them through Zod (`src/lib/verified-session.ts`).
Measured in one session, old code then new, 40 signed-in `/products` navigations
each, `NAV_TIMING=1` on a dev server against Docker Postgres: before,
`proxy.claims` 1.3 ms p50 / 1.8 p95 **plus** `session.auth` 53.8 p50 / 116.1 p95;
after, `proxy.claims` 1.3 p50 / 2.0 p95 and **zero `session.auth` samples** (0 of
40 navigations). `proxy.auth` was 0 in both windows. Client wall clock was not
comparable across windows in dev (566.5–621.2 ms p50 for full-document fetches,
spread wider than the delta), so only the layer delta is claimed: about 54 ms p50
/ 116 ms p95 of server time removed from a navigation. Route handlers and Server
Actions read the same headers; the panel route and the CSV export both answered
200 with data and the signed-out equivalent got a 307 to `/sign-in`.

The trade-off is the new row above: the proxy is now the single gate. The
consequences are deliberate — the header is overwritten rather than merged, a
browser-supplied `x-verified-*` never survives, a missing header is "signed out"
rather than "verify again", and every tenant query still takes its user id from
that verified session, with RLS deciding access. Server revocation is unaffected:
it is still invisible until the access token expires, for the same JWKS reason.
